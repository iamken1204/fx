5  	## Declaring Work Ready
6  	
7  	Do not say the work is "ready", "done", "good to go", "complete", or similar until you have personally run the binary and exercised the change on its happy path. A passing test suite is necessary, not sufficient — tests in this repo do not always construct the full runtime, attach a TTY, or spawn background threads, so they will not catch startup crashes, render regressions, or thread-lifetime bugs.
8  	
9  	Before reporting the work as ready:
10 	
11 	1. Build succeeds.
12 	2. Focused tests for the changed path pass locally.
13 	3. The **Full CI** run for the exact current commit passes on every required Linux and macOS runner.
14 	4. Run the built binary locally and drive at least one real interaction that exercises the change end to end.
15 	5. Confirm the process did not abort, stderr is clean, and the behavior matches what you are about to tell the user.
16 	
17 	If you cannot run the binary in your environment, say so explicitly and ask the user to verify. Do not silently skip this step and declare the work ready. "The tests pass" is not a substitute for running the app.
18 	
19 	### Always use the built binary in this repo
20 	
21 	When running fx for verification, **always use the freshly-built binary at** **`./zig-out/bin/fx`** from this checkout. Never run `fx` from `PATH`, never rely on whatever is at `~/.fx/bin/fx`, and never assume an installed copy reflects your change.
22 	
23 	* The user may have an older `fx` on their PATH (e.g. installed via `fx upgrade` or the CDN install script). Running that one will not exercise your edits.
24 	
25 	* `zig build` writes to `zig-out/bin/fx`. That is the only binary that contains your latest change.
26 	
27 	* When a user reports "still not working" after you believe you fixed something, do not assume they are running the wrong binary. Assume your fix is incomplete and investigate further. If you genuinely suspect a PATH mismatch, ask — do not silently copy binaries into `~/.fx/bin/`.
28 	
29 	* In any shell invocation — tmux, direct run, scripts — reference fx as `/Users/<you>/path/to/repo/zig-out/bin/fx` (absolute) or `./zig-out/bin/fx` (when cwd is the repo root). Bare `fx` is always wrong for dev verification.

32 	
33 	This project is written in **Zig 0.16+**. There is no Node.js runtime, no `package.json` at the root, and no JavaScript build step for the main binary.
34 	
35 	Build and test commands:
36 	
37 	```bash
38 	zig build          # build the binary
39 	zig build test     # run all unit tests
40 	zig build run      # build and run
41 	zig fmt src/       # format all source files
42 	```
43 	
44 	The test suites under `tests/` use Bun but are separate from the Zig codebase. See **Testing** below.

46 	## Code Style
47 	
48 	* Format all Zig source with `zig fmt` before committing. The canonical check is `zig fmt src/`.
49 	
50 	* Do not use emojis in code, output, or documentation. Unicode symbols (e.g. checkmark, arrow) are acceptable.
51 	
52 	* In documentation, never use double hyphens (`--`) as a dash. Use an emdash (—) sparingly, or rewrite to avoid dashes.
53 	
54 	* CLI flags use kebab-case (e.g. `--no-save`, `--json`). Never use camelCase for flags.
55 	
56 	* Prefer `snake_case` for all Zig identifiers. Types use `PascalCase` per Zig convention.
57 	
58 	* Keep `pub` surface area minimal. Only mark declarations `pub` when they are used outside the file.

60 	## Architecture
61 	
62 	Key rules:
63 	
64 	* `src/main.zig` is the composition root. Do not add leaf feature logic here.
65 	
66 	* `src/core/` owns contracts, runtimes, config, sessions, permissions, MCP, skills.
67 	
68 	* `src/tools/` owns built-in tool implementations. Generic tool contracts and dispatch live in `src/core/tooling/`. Default tool specs are centralized in `src/core/tooling/tool_specs.zig` or `src/builtins/tools.zig`, not in individual tool files.
69 	
70 	* `src/ui/` owns terminal rendering, event loop, input, transcript. It must not own product state.
71 	
72 	* `src/gateway/` owns provider transport. It must not absorb product-state logic.
73 	
74 	* `src/acp/` owns the ACP (Agent Client Protocol) JSON-RPC 2.0 server.

76 	### Adding a Feature
77 	
78 	Before implementing, answer in order:
79 	
80 	1. Which module owns the behavior?
81 	2. What is the typed contract?
82 	3. Does it need persistence?
83 	4. Does it need both text and JSON output?
84 	5. What docs and tests land with it?
85 	6. How is its deterministic E2E owner classified in the macOS arm64 PGSO corpus?
86 	
87 	If unclear, define the contract first.
88 	
89 	Every root `tests/e2e/*.test.ts` file must have exactly one classification in
90 	`scripts/pgso/corpus.json`:
91 	
92 	* **Training:** common or performance-sensitive product behavior that should
93 	  influence LLVM's hot and cold decisions
94 	
95 	* **Verification-only:** important correctness, recovery, security, or rare
96 	  behavior that the final candidate must pass without making it hot
97 	
98 	* **Intentional exclusion:** nondeterministic, live-network, credentialed,
99 	  sound-related, or harness-only coverage, with a concrete reason
100	
101	New tests inside an already classified file inherit that file's classification,
102	but feature work must reconsider whether the existing classification still
103	matches the file's product role. When removing a feature or E2E owner, remove
104	its stale corpus entry. Normal PR CI loads the corpus and rejects missing,
105	duplicate, stale, or unclassified files without running the expensive PGSO
106	qualification.

109	
110	1. Add the spec to `src/core/slash_commands/command_specs.zig`
111	2. Add dispatch wiring in `src/core/cli/cli_surface.zig`
112	3. Add a snapshot type if it has structured output
113	4. Render text and JSON from the same snapshot via `src/core/output/output_contracts.zig`

117	## Configuration and State
118	
119	Profile configuration and runtime state lives under `~/.fx/`. Project `.fx.json` contains committed project defaults only.
120	
121	Config precedence (highest wins):
122	
123	1. Environment variables such as `FX_MODEL`, `FX_PERMISSION_MODE`, and `FX_MAX_AGENT_STEPS`
124	2. `~/.fx/settings.json` → `workspaces["<workspace_path>"]` (profile workspace overrides)
125	3. `~/.fx/settings.json` top-level (profile global settings)
126	4. `<workspace>/.fx.json` (committed project defaults)
127	5. Built-in defaults
128	
129	Project `.fx.json` accepts only repo-safe defaults: `sandbox`, `max_agent_steps`, `max_tool_result_bytes`, and `context`. Profile-owned keys such as `model`, `effort`, `fast_mode`, `slash_menu_categories`, `startup_scrollback`, `prompt_history`, `statusLine`, `skill_match_fuzzy`, `first_call_tool_choice`, `auto_upgrade`, `permission_mode`, `credential_source`, and `permission` are ignored from project config before their values are parsed.
130	
131	Runtime state lives under `~/.fx/sessions/<session-id>/` (`session.json`, `background/`, `subagent/`, `logs/`). Sessions are global and portable across workspaces. Each session tracks its `workspace_root`, which updates when resumed in a different workspace. A subagent child is an internal ordinary session with its own history. Its parent owns one bounded `subagent/children.json` registry, and the child carries only an immutable owner marker. Child sessions stay out of ordinary session discovery and cannot be resumed directly. A first `subagent.message` creates a named persistent child in that parent; later messages continue it, and optional instructions replace only its child-specific system overlay.

133	## Permissions
134	
135	Security is permission-first. All sensitive tool behavior must integrate with `src/core/permissions/permissions.zig`.
136	
137	* `permission_mode` controls baseline (`ask`, `auto`, or `yolo`). Yolo bypasses fx permission policy and uses an effective sandbox of `none` without rewriting saved sandbox configuration
138	
139	* Configured denies are evaluated before saved-session rules; an exact saved-session deny can narrow a configured allow, while an exact saved-session allow can satisfy an unresolved configured ask
140	
141	* Session `always` approvals are non-persistent; command approvals match the exact command while other grant categories may use patterns
142	
143	* `/permissions remember allow|deny <tool-name> <arguments-json>` confirms and stores an exact rule only for an active saved session; list and revoke those rules by their stable IDs
144	
145	* Routine parsed development commands and reversible new-file creation can execute without model review after configured and saved-session policy. Every remaining unresolved `auto` action receives one narrow security review using the exact unmasked action and targets, origin and call identity, optional host-proven current-branch evidence, and bounded unmasked terminal-safe excerpts of earlier current-turn tool results. A text match between the action and prior tool output is evidence to inspect, not proof of prompt injection or malicious activity. Prepared file mutations and static root tools omit task text. Reviewed commands, dynamic tools, and subagent actions also receive bounded unmasked canonical current, first, and recent root requests plus explicit omission counts; the reviewer may use that context only to distinguish trusted user intent from malicious or injected influence, never to judge task quality, alignment, or authorization. Assistant prose, permission feedback, compacted summaries, the pending tool group, later results, and tool or repository text never become authority
146	
147	* The reviewer returns `caution` only for concrete prompt injection or malicious activity. Destructive, risky, external, public, remote, unrequested, or task-conflicting actions clear when they are not malicious. A `clear` review authorizes only the exact unchanged action. A `caution`, incomplete-evidence result, or unavailable review holds only that action, returns guidance to the agent, and never opens a human permission screen, disables tools, or ends the turn
148	
149	* Exact cautions and deterministic incomplete-evidence results are reused only for the current turn. An unavailable outcome is not cached as a security judgment, but the same exact action spends at most one unavailable transport attempt per turn; changed actions remain independently reviewable until the bounded current-turn transport budget is exhausted. Legacy `permission_request_id` input is rejected without prompting
150	
151	Do not bypass the permission system for new tools.

153	## Zig-Specific Patterns
154	
155	### Memory
156	
157	* Allocators are passed explicitly. Never use a global allocator.
158	
159	* Free what you allocate. Use `defer` for cleanup at the call site.
160	
161	* Prefer `ArenaAllocator` for request-scoped work that can be freed in bulk.
162	
163	* When a function returns allocated memory, document who owns it (caller or callee).
164	
165	### Error Handling
166	
167	* Return errors rather than panicking. `@panic` is for programmer bugs, not runtime conditions.
168	
169	* Use `errdefer` to clean up partial state on error paths.
170	
171	* Prefer specific error sets over `anyerror` when the set is bounded.
172	
173	### Strings and JSON
174	
175	* Zig strings are `[]const u8`. There is no implicit null termination.
176	
177	* For JSON serialization, use `std.json.Stringify.value` with an allocating writer (`std.Io.Writer.Allocating`).
178	
179	* For JSON string escaping (writing raw JSON), use the project's `writeJsonStr` helper in `src/acp/jsonrpc.zig` rather than assuming `std.json.encodeJsonString` exists.
180	
181	* Zig 0.16 uses `std.Io.File.stdin()` / `.stdout()` / `.stderr()`, not `std.io.getStdIn()`.
182	
183	### I/O (Zig 0.16 "Juicy Main")
184	
185	* `main` uses `pub fn main(init: std.process.Init) !void` signature.
186	
187	* All I/O goes through `std.Io`, passed explicitly or via the project's `src/core/shared/io.zig` helper (`io_mod.getIo()`).
188	
189	* File operations use `std.Io.Dir` and `std.Io.File` (not `std.fs`). Most methods require an `io` parameter.
190	
191	* Environment variables: use `io_mod.getenv(key)` (returns `?[]const u8`), not `std.process.getEnvVarOwned`.
192	
193	* Time: use `io_mod.milliTimestamp()`, `io_mod.nanoTimestamp()`, `io_mod.sleep(ns)`.
194	
195	* File reading: use `io_mod.readFileToEnd(alloc, &file, max_bytes)`.
196	
197	* Realpath: use `io_mod.realpathAlloc(alloc, path)` or `io_mod.dirRealpathAlloc(alloc, dir, sub_path)`.
198	
199	* Process spawning: use `std.process.spawn(io, opts)` and `std.process.run(alloc, io, opts)`.
200	
201	* Mutexes: `std.Io.Mutex`, initialized with `.init`, locked with `.lockUncancelable(io)`.
202	
203	* HTTP: `std.http.Client` requires `.io = io_mod.getIo()` in its initializer.
204	
205	* `std.mem` renames: `trimLeft` is `trimStart`, `trimRight` is `trimEnd`, `indexOf` is `find`, `indexOfScalar` is `findScalar`.
206	
207	* `ArrayList(T)` initializes with `.empty` (not `.{}`).
208	
209	### Testing
210	
211	* Zig unit tests go inside the source file they test, using `test "description" { ... }` blocks.
212	
213	* Run the narrowest relevant tests while developing. The complete `zig build test` suite runs in ReleaseSafe in **Full CI** after the feature branch is pushed, and it must pass before the draft PR is marked ready.
214	
215	* Use `std.testing.expect`, `std.testing.expectEqual`, `std.testing.expectEqualStrings` for assertions.
216	
217	* In test blocks, use `std.testing.io` for the `Io` parameter. `io_mod.getIo()` automatically returns `std.testing.io` in test builds.
218	
219	* Use `io_mod.dirRealpathAlloc(alloc, dir, sub_path)` to resolve paths within `std.testing.tmpDir()`.

247	## Pull Request Classification
248	
249	Every pull request must have exactly one `type:` label, chosen by its primary intent:
250	
251	* `type: bug`: fixes incorrect behavior
252	
253	* `type: feature`: adds a new user-facing capability
254	
255	* `type: improvement`: improves existing user-facing behavior
256	
257	* `type: docs`: changes documentation only
258	
259	* `type: maintenance`: changes internal tooling, dependencies, CI, or implementation structure without a user-facing behavior change
260	
261	* `type: release`: prepares or repairs a release
262	
263	* `type: security`: fixes or hardens a security boundary
264	
265	Assign the label when the PR is opened and keep it accurate when the PR changes. If the authenticated contributor cannot manage labels, state the required label and keep the PR in draft until a maintainer or repository agent applies it. For a mixed PR, choose the label that describes the primary reason the PR exists. If that is ambiguous, ask before applying or changing the label.
266	
267	Keep PR titles as clean imperative sentences, such as `Restore feedback report file clipboard`. Do not add bracketed prefixes such as `[bug]`, `[feature]`, or `[improvement]`. Type belongs in the label, not the title.

269	## Full CI on Feature Branches
270	
271	Do not run the complete deterministic test suite locally as the default development loop. Run the focused test for the changed path, build the binary, and exercise that path with `./zig-out/bin/fx`.
272	
273	After the focused checks pass, create a clean checkpoint commit, push the non-`main` feature branch, and open a draft PR immediately. `.github/workflows/full-ci.yml` runs the following on all four supported native runner architectures:
274	
275	* `ubuntu-24.04` (x86_64)
276	* `ubuntu-24.04-arm` (aarch64)
277	* `macos-15-intel` (x86_64)
278	* `macos-15` (aarch64)
279	
280	The native matrix builds, tests, and smoke-tests ReleaseSafe on every platform; formatting and the public-surface audit run in those ReleaseSafe jobs. The E2E matrix runs four duration-balanced, isolated ReleaseSafe shards per platform with Bun and tmux. Checked-in weights assign every test file to exactly one shard on each platform, and files inside each shard run sequentially in separate Bun processes so terminal fixtures and process state cannot leak between files. A failed file receives one bounded retry after its tmux server is reset. Live model evals remain separate because they require credentials and are not deterministic.
281	
282	A Full CI result is valid only when it belongs to the exact current commit and all four `Full suite (...)` jobs succeed. Each platform aggregate requires its ReleaseSafe native check plus all four ReleaseSafe E2E shards. Do not mark the draft PR ready or request review from a stale, partial, queued, cancelled, skipped, or failed run. If Full CI fails, make the smallest repair, rerun the focused local proof, push the new commit to the same draft PR, and wait for Full CI on the new exact commit. After CI passes, run the final ship gate and mark the PR ready only when it reports `SHIP` for that exact commit.

284	## Reproducing Render Bugs
285	
286	fx's rendering is inline by default and deliberately emits a small ANSI subset. Three owner classes are the narrow exceptions, and each takes the alternate buffer exclusively through `AlternateScreenOwner` in `src/ui/shell_runtime.zig`: interactive permission review, the full-transcript screen, and catalog menus. Only one class may own the buffer at a time, and each must leave it and restore the main grid, composer, cursor, paste, mouse, focus, and keyboard modes when it closes. Transcript rendering, question prompts, command-output expansion, and subagent delegation remain inline. Three tools exist for reproducing and regression-proofing render bugs:
287	
288	### tmux (live TTY repros)
289	
290	Best for resize and SIGWINCH interactions. The helper in `tests/e2e/tmux-helpers.ts` exposes `resizeWindow(cols, rows)`, `capturePaneGrid()`, and `capturePaneEscapes()`. See `tests/e2e/tui-resize.test.ts` for the canonical resize matrix.
291	
292	```bash
293	cd tests/e2e && bun test tui-resize.test.ts
294	```
295	
296	### Debug terminal recording and replay
297	
298	Set `FX_DEBUG_RECORD=1` to create an automatic private tape under
299	`~/.fx/recordings/`. Set `FX_DEBUG_RECORD_SILENT_BANNER=1` as well when the
300	developer-only recording notice must stay out of the inline transcript during
301	a screen share. The notice remains available in the Ctrl+O full transcript.
302	Use `FX_RECORD=<path>` when a test or investigation needs an exact destination.
303	Recording dumps every byte fx writes and every resize into a framed binary tape.
304	Replay the tape through the built-in virtual terminal:
305	
306	```bash
307	FX_DEBUG_RECORD=1 ./zig-out/bin/fx
308	FX_RECORD=/tmp/bug.fxtape ./zig-out/bin/fx
309	./zig-out/bin/fx replay /tmp/bug.fxtape
310	./zig-out/bin/fx replay /tmp/bug.fxtape --frames
311	./zig-out/bin/fx replay /tmp/bug.fxtape --json
312	./zig-out/bin/fx replay /tmp/bug.fxtape --golden out.txt
313	```
314	
315	The tape is deterministic — any reviewer can replay it without a TTY, and a golden file can be checked in as a regression test.
316	
317	### Shared terminal engine (sub-second unit tests)
318	
319	`src/core/terminal/engine.zig` is the shared bounded text-terminal engine for hosted terminal sessions, recovery, replay, and deterministic rendering tests. `src/ui/resize_tests.zig` drives `TranscriptRuntime` against it in process so resize behavior can be exercised with no fd or timing dependence.
320	
321	```bash
322	zig build test                      # runs every VT and resize test
323	```
324	
325	When a tmux or tape-based scenario exposes a bug, reproduce it as a Zig unit test in `resize_tests.zig` (or a new sibling) before fixing. The test lands the fix as a regression.

327	## Benchmarks
328	
329	Startup latency benchmarks live in `benchmarks/` and run in CI via `.github/workflows/bench.yml`.
330	
331	```bash
332	./benchmarks/startup.sh            # full run (100 iterations, builds ReleaseSafe, needs hyperfine)
333	./benchmarks/startup.sh --quick    # quick run (20 iterations)
334	```
335	
336	The CI workflow builds a ReleaseSafe binary, measures six CLI paths with hyperfine, and enforces per-command latency budgets. PRs that exceed a budget fail the check. On `main`, results are uploaded to Vercel Blob for historical tracking.
337	
338	The startup benchmark uses `FX_BENCH=1`, an environment variable that runs through arg parsing and CLI dispatch, then exits before TTY initialization. This lives in `src/core/app/app_entry_runtime.zig`.
339	
340	Current raw wall-clock contract:
341	
342	* Linux CI: 2ms for every command
343	* Non-Linux local runs: informational raw means
344	
345	The Linux CI runner is the authoritative product budget. Local macOS process
346	and dynamic-loader floors vary enough to exceed 2ms independently of fx, so
347	local runs report raw means without assigning a substitute product budget. The
348	process baseline is diagnostic only and is never subtracted.
349	
350	When adding features, consider their impact on startup latency. The `fx help` path is the baseline cold-start benchmark.

352	## Binary Size Observability
353	
354	Every pull request runs `.github/workflows/binary-size.yml` across Linux x86_64,
355	Linux arm64, macOS x86_64, and macOS arm64. Each matrix job builds the pull
356	request merge commit and its base commit as stripped ReleaseSafe binaries on
357	the same native runner, then reports the exact byte and MiB delta plus ELF or
358	Mach-O section changes.
359	
360	Each platform check is informational. An increase of at least 52,429 bytes
361	(0.050000 MiB) emits a warning and retains that platform's binaries for
362	investigation, but does not reject the pull request. Investigate notable
363	unexplained growth before changing the threshold. The full macOS arm64 PGSO
364	release qualification remains authoritative for the 7.800 MiB production
365	ceiling and performance gates.

377	## Releasing
378	
379	Releases use a two-workflow pipeline. The maintainer controls the changelog voice and format.
380	
381	### Automated flow (preferred)
382	
383	1. Go to **Actions > Prepare Release** on GitHub
384	2. Select the bump type (`patch`, `minor`, or `major`) and run the workflow
385	3. The workflow bumps the version, feeds the actual `git diff` to an LLM to draft the changelog, and opens a PR
386	4. Review the PR — edit the AI-drafted changelog if needed — then merge
387	5. The existing `release.yml` detects the version change and handles build, publish, tagging, and the GitHub Release
388	
389	The `prepare-release.yml` workflow uses the Vercel AI Gateway (`AI_GATEWAY_API_KEY` secret) to generate the changelog from the real code diff, not from commit messages or PR descriptions.
390	
391	### Manual flow
392	
393	To prepare a release by hand:
394	
395	1. Create a branch (e.g. `prepare-v0.3.0`)
396	2. Bump `pub const version` in `src/main.zig`
397	3. Write the changelog entry in `CHANGELOG.md` at the top, under a new `## <version>` heading, wrapped in `<!-- release:start -->` and `<!-- release:end -->` markers. Remove the markers from the previous release entry so only the new release has them.
398	4. Update `README.md` install example version
399	5. Open a PR and merge to `main`
